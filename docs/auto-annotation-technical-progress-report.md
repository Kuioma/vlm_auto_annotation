# 视频自动标注项目技术进展汇报

> 汇报日期：2026-07-19  
> 当前分支：`feat/ordered-action-annotation`

## 一、总体进展

项目已经从“可重复验证的 Mock 原型”推进到“真实 vLLM 接口、有序多视角标注、可断点续跑批处理”的阶段。

目前已经完成以下核心能力：

1. 建立基于真实视频 PTS 的确定性标注流水线；
2. 接入 OpenAI-compatible vLLM 服务；
3. 实现有序闭集动作的两阶段、多视角边界定位；
4. 实现面向 WA2 数据集的批量发现、并发、重试和断点续跑；
5. 建立严格的结构化输出校验、运行身份追踪和原子产物机制；
6. 当前完整测试集共 370 项，全部通过。

需要特别说明：当前工程链路已经较完整，但仓库内尚无正式的真实 GPU 运行报告、人工 Gold Set 评测结果或模型精度基线，因此现阶段能够确认的是“系统可运行且工程约束有效”，还不能确认“模型标注质量已经达到生产要求”。

## 二、技术尝试、发现的问题与改进

### 2.1 第一阶段：确定性核心标注切片

#### 技术尝试

- 使用 `ffprobe` 获取视频帧的真实 PTS、时长和帧率；
- 使用低帧率全局粗标注和高帧率局部边界细化的两阶段流程；
- 使用 Schema 和 Ontology 动态定义标注字段及闭集词汇；
- 使用脚本化 Mock 后端验证完整推理链路；
- 将中间产物和最终 JSONL 进行确定性、原子化写入；
- 使用内容哈希、模型身份、Prompt 版本和 Stage 版本生成可复现的 `run_id`。

#### 发现的问题

- Mock 后端只能验证工程流程，无法验证真实模型的响应质量；
- 让模型自由生成 Segment 时，可能出现步骤缺失、顺序错误、时间空隙或重叠；
- 直接使用浮点秒或模型生成的任意时间值，容易出现精度和边界语义不一致；
- 非法 Schema/Ontology 值、错误 Segment ID 和异常时间线必须被视为不可信输出。

#### 改进方式

- 内部统一使用绝对整数毫秒和半开区间 `[start_ms, end_ms)`；
- 在模型响应进入流水线时同时执行 JSON Schema 和严格 Pydantic 校验；
- 在产生任何输出副作用前，预校验完整 Manifest、数据集 ID、Schema/Ontology ID 和输出路径；
- 对视频、配置、Manifest、Schema、Ontology、模型和行为版本进行哈希，保证结果可追踪、可复现；
- 对 Artifact 和 JSONL 使用 `fsync` 加原子替换，防止中断后留下半写文件。

### 2.2 第二阶段：接入真实 vLLM

#### 技术尝试

- 增加 OpenAI-compatible `/models` 和 `/chat/completions` 调用；
- 支持目标模型、模型 revision、vLLM 版本、超时、温度、Seed 和最大输出 Token 配置；
- 使用 JSON Schema Structured Output 约束模型响应；
- 使用 FFmpeg 将请求区间裁剪到受控的本地 Media Staging 目录；
- 支持视频输入和编号接触图图片输入。

#### 发现的问题

- vLLM 服务可能可访问，但并未加载配置中的目标模型；
- 服务可能返回 HTTP 错误、空响应、非 JSON 内容或不符合 Schema 的 JSON；
- vLLM 0.24 在结构化输出参数校验失败后，API 进程与 EngineCore 的多模态缓存可能不一致；
- 直接暴露任意本地路径存在路径逃逸、符号链接和临时文件残留风险。

#### 改进方式

- 正式推理前调用 `/models` 做健康检查和模型身份校验；
- 将传输错误与响应格式错误分类，便于重试和故障诊断；
- 对响应内容执行二次 JSON 解析和 Schema 校验；
- 为每一次媒体请求加入 Attempt 级 UUID，避免重试复用异常的多模态缓存；
- 只接受受控的本地文件 URI，Staging 目录必须存在且不得使用不安全的符号链接；
- 无论请求成功还是失败，都清理本次临时媒体工作目录。

### 2.3 第三阶段：有序闭集动作、多视角、帧索引标注

#### 技术尝试

针对 `pick_up → transfer → place` 等动作顺序预先确定的工业任务，引入独立的有序标注处理器：

1. 从 `task.yaml` 加载任意长度的有序动作集合；
2. 从 Ontology 加载每个动作的定义、边界规则以及正反视觉线索；
3. 在全视频低帧率多视角接触图中定位 N 个动作之间的 N−1 个粗边界；
4. 围绕每个粗边界生成高帧率局部多视角窗口；
5. 独立细化每一个边界；
6. 根据边界重建连续覆盖全视频的 Segment。

最终时间线固定为：

```text
A1 = [0, b1)
A2 = [b1, b2)
...
An = [b(n-1), duration_ms)
```

#### 发现的问题

- 对固定工序而言，自由语义分段过于灵活，模型可能新增、删除、重排或改名动作；
- 直接让模型输出毫秒时间不稳定，且难以证明时间点对应真实视频帧；
- 单一头部相机可能存在遮挡，物体离开主相机画面也容易被误判为动作完成；
- 全局低帧率适合定位大致范围，但不适合确定精确边界；
- 如果细化阶段看到粗阶段候选帧，容易受到锚定偏差影响；
- 多相机视频只有在时长、帧率和 PTS 完全同步时才能安全组合。

#### 改进方式

- 动作数量、语义、顺序和名称由 Task、Schema、Ontology 共同固定，模型不得修改；
- 模型只返回 `F000`、`F001` 等帧索引，由系统映射回真实源视频 PTS；
- 每个边界定义为“第一张能够确认后一步已经开始、前一步已经结束的采样帧”；
- 同时使用头部和有效腕部相机，强调不能仅根据物体离开主视角判断边界；
- 全局阶段使用低帧率定位，局部阶段使用更高帧率细化；
- 局部细化 Prompt 不暴露粗阶段候选时间和证据，只使用粗结果选择窗口，降低锚定偏差；
- 在生成多视角接触图前，严格校验所有相机的时长、标称帧率和逐帧 PTS；
- 强制 N−1 个边界严格递增且位于时间线内部，从结构上保证 Segment 连续、无空隙、无重叠。

### 2.4 时间线冲突处理

#### 发现的问题

旧的通用粗标注和独立边界细化流程中，相邻不同标签的 Segment 可能产生小范围重叠。如果一律拒绝，少量可解释的边界误差无法自动恢复；如果直接裁剪，又可能掩盖模型错误。

#### 改进方式

增加受控重叠解决策略：

- 只有重叠量不超过配置阈值时才允许自动处理；
- 两个 Segment 必须在重叠范围内具有共同边界证据；
- 从共同证据中选择最接近重叠中点的时间作为新边界；
- 将原始边界、重叠量、解决边界和策略写入质量信号；
- 不满足上述条件时仍拒绝结果，避免静默修正严重错误。

### 2.5 第四阶段：批量运行与工程可靠性

#### 技术尝试

- 将批量 Source、单条 Processor 和 Runner 解耦为插件；
- 实现 WA2 Episode 和多视角媒体发现；
- 支持外部命令 Processor；
- 支持有界并发、失败隔离、重试、断点续跑和 Fail-fast；
- 记录逐 Item、逐 Attempt 的输入、输出、日志、失败原因和 Artifact；
- 聚合生成 `output.jsonl`、`output_index.jsonl`、`failures.jsonl`、`summary.json` 和 `invocations.json`。

#### 发现的问题

- 单进程逐条执行在超时、崩溃或部分失败后难以恢复；
- 输入、模型、脚本或参数变化后，不能安全地无条件复用旧结果；
- 超时或取消的外部处理器可能留下子进程继续写文件；
- 刷新失败可能覆盖之前已经提交的正确结果；
- 并发运行时需要防止同一 Item 重复分配 Attempt，或多个相同 Run 同时修改状态。

#### 改进方式

- 使用 Processor Identity 和 Input Fingerprint 隔离不同处理版本与不同输入；
- 相同身份和输入下跳过已成功提交的 Item，只有变化的 Item 重新执行；
- 将尝试次数作为持久化预算，支持可重试错误和终止错误分类；
- 成功 Marker 作为每个 Item 的最后一次原子写入，只有 Marker 提交后才视为完成；
- Forced Refresh 失败时保留 Last-known-good 结果；
- 超时或取消时终止整个外部进程组并保存 stdout/stderr；
- 同一 Run 使用进程级独占锁，Attempt 分配采用原子操作；
- `--plan-only` 可在无输出副作用的情况下检查插件、输入和待处理范围。

## 四、当前局限与风险

1. **真实模型效果尚未形成证据**  
   已有真实 vLLM Adapter 和可执行配置，但仓库内没有提交真实 GPU/Qwen3.6 运行报告、原始响应样本、吞吐数据或准确率指标。

2. **缺少 Gold Set 和质量基线**  
   尚未计算动作准确率、对象准确率、序列准确率、Temporal IoU、边界误差，以及边界误差不超过 2 秒的比例。

3. **长视频尚未支持**  
   当前核心流水线和有序 Processor 都只接受单个、最长约 120 秒的视频 Chunk，尚未实现跨 Chunk 合并。

4. **接触图规模受限**  
   单张接触图最多 40 个时间单元。更长视频或更高采样率需要分层采样或多张接触图方案。

5. **批处理状态仍为文件式实现**  
   当前已经具备持久化、锁、重试和恢复，但尚未实现设计中的 SQLite WAL、Lease、Endpoint Pool 和多机任务队列。

6. **示例配置可移植性不足**  
   示例中存在本机数据集和 Media Staging 的绝对路径，需要改为环境变量、部署配置或模板参数。

7. **并发默认值需要真实基准校准**  
   当前示例使用 `concurrency: 15`，但 27B 多模态模型更适合从 `limit: 1`、`concurrency: 2` 的 Canary 开始，根据显存、延迟和失败率逐步增加。

8. **仓库说明已经落后于实现**  
   当前 `AGENTS.md` 和部分本地 Skill 仍描述“只有 Mock、没有真实 vLLM 和批处理”，需要与 Feature 分支实现同步。

## 五、下一步建议

### P0：验证真实模型闭环

1. 使用 `limit: 1`、`concurrency: 1~2` 运行真实 GPU Canary；
2. 保存模型原始响应、结构化结果、接触图、Prompt、显存、延迟和失败类型；
3. 人工复核 10～30 条代表性视频，确认动作顺序和边界定义是否合理；
4. 根据真实失败样本调整 Ontology 视觉线索、采样率和细化窗口。

### P1：建立质量评测

1. 建立覆盖不同动作、视角、遮挡和时长的人工 Gold Set；
2. 实现动作、对象、序列、Temporal IoU 和边界绝对误差指标；
3. 报告边界误差在 0.5 秒、1 秒、2 秒内的比例；
4. 将质量结果与采样率、细化窗口、模型版本和并发参数关联。

### P2：提升批量可用性

1. 将示例中的绝对路径参数化；
2. 增加正式运行前的自动 Canary 和资源检查；
3. 增加失败分类汇总和重试建议；
4. 根据真实 GPU 基准确定安全并发上限。

### P3：扩展能力

1. 实现长视频多 Chunk 执行和跨块边界合并；
2. 增加 Parquet 导出和离线评测命令；
3. 根据规模需要再引入 SQLite Lease、Endpoint Pool 或分布式调度；
4. 同步更新仓库 `AGENTS.md` 和本地 Skills，消除文档与实现偏差。

## 六、阶段性结论

当前项目已经完成从概念验证到可批量执行工程框架的主要跨越：输入契约、视频时间基准、真实推理适配、有序动作约束、多视角证据、局部边界细化、结果校验、断点续跑和审计产物均已有实现和测试覆盖。

下一阶段的关键不再是继续增加工程模块，而是通过真实 GPU Canary 和人工 Gold Set 回答两个核心问题：

1. 当前模型在真实工业视频上的动作与边界质量达到什么水平；
2. 采样率、细化窗口、视角组合和并发参数应如何根据数据确定。

只有完成这一步，才能从“工程链路可用”推进到“标注质量可量化、可验收、可规模化”。
